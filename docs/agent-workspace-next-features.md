# AIインターフェース設計／レビュー: v0.0.3の次に加える機能

## 1. 結論

- 判定: **次は「仕様とプレビューの動作一致」を最優先にする。**
- 主要判断: v0.0.3には案件管理、プロバイダー接続、仕様確認、HTML生成がある。次の価値は生成件数の増加より、利用者が「何を実際に確かめられるか」を判断できることにある。
- 最大リスク: 見た目の整ったプレビューで、検証したい操作が動くと思い込むこと。現在の生成HTMLは画面遷移と入力値の表示更新を中心に実装している。これは本アプリの目的に対する品質上の不足である。

## 2. 対象と前提

| 達成したい結果 | 仕様案を、検証できる範囲が明確な試作品へ仕上げ、必要な修正を短い往復で終える |
| AIの役割 | 会話と仕様の提案・共同編集。HTML生成と構造検証は決定的なローカル処理 |
| 外部システム | OpenAI Codex／Anthropic、Pi SDK、ローカルのHTML生成環境 |
| 観測事実 | `builder/wireframe-runtime.js`は画面切替と`field`／`select`の値表示を実装する。`panel`本文の条件付き差し替えや保存処理はない |
| 観測事実 | `WireframeReviewSpec.swift`は配色、入力形式、遷移先を検査するが、仮説に必要な動作とHTMLの一致は判定しない |
| 観測事実 | `PiChatService.swift`は会話履歴全体と現在の仕様を送る。送信範囲の選択UIはない |
| 観測事実 | 案件は自動保存されるが、同一案件の仕様版を比較・復元する操作はない |

## 4. 五段階の状態設計

| 段階 | 状態 | 利用者に見せる情報 | 可能な操作 | 失敗 | 復旧 |
|---|---|---|---|---|---|
| 構成 | 接続済み／ログアウト済み | 案件のモデル、接続状態、送信対象の既定値 | 接続、モデル変更、文脈設定 | 認証失敗 | 再接続。案件は保持 |
| 入力 | 仮説と仕様の編集中 | 今回検証する操作、AIに渡す会話・仕様 | 指示、対象画面の選択、文脈除外 | 意図の誤解 | 局所修正し、元版を保持 |
| 計算 | 提案中／ビルド中／検査中 | 現在工程と実行対象の仕様版 | 別案件へ移動、中止 | 形式・接続・生成失敗 | 該当工程から再試行 |

| 行動 | 案件の確認完了 | 検証できた操作、未確認点、生成元仕様版 | 保存、版復元、確認記録 | 古い成果物の取り違え | 現仕様から再生成 |

## 5. 主要な設計判断

### D-01: v0.0.4は操作の実装範囲を明示する

- 対象状態: 仕様確認からHTML生成、プレビューまで。
- 変更前または現状: `action`は画面遷移、`value`は入力値の表示を行う。仕様文にはそれ以上の挙動を説明できるため、実物との差が生じる。
- 提案: 仕様の各主要操作を「実際に動く」「画面遷移のみ」「表示のみ」「未対応」に分類し、生成前とプレビュー内に同じ表示を置く。検証したい仮説に必要な操作が未対応なら、生成は可能でも「操作確認待ち」と明示する。代表例の語り口切替は、本文が実際に変わる実装を追加するか、静的比較と明記する。
- 根拠: 構造検証の合格は仮説の検証可能性を証明しない。Appleは生成結果を利用者が調整し判断できる設計を推奨する。[Appleの生成AIガイド](https://developer.apple.com/design/human-interface-guidelines/generative-ai)
- トレードオフ: 非対応を明示することで「すぐ完成した」印象は弱まる。
- 受入条件: 仕様に記載した主要操作と、生成HTMLで実際に起きる状態変化を一対一で照合できる。未対応の操作を動作済みと表示しない。
- 未検証事項: 利用者が必要とする動作の粒度。

### D-02: AIへ渡す文脈を案件内で確認・除外する

- 対象状態: 送信と仕様案の生成。
- 変更前または現状: 会話履歴全体と現在仕様を自動的にプロンプトへ含める。
- 提案: 送信欄の近くに「送信する情報」を常設し、今回の入力、過去の会話、現在仕様を確認・除外できるようにする。既定の除外状態は案件ごとに保存する。送信先モデルと履歴件数を表示する。通常操作は一クリックで送信し、詳細は必要時に開く。
- 根拠: 外部送信は取り消せず、情報量は応答時間と利用量にも影響する。何を送るかを利用者が選べることは品質と制御の両方に関係する。
- トレードオフ: 文脈を減らすと回答の一貫性が下がる可能性がある。
- 受入条件: 除外した履歴・仕様がPiへの入力に含まれない。送信前に接続先と含まれる文脈を確認できる。
- 未検証事項: 各プロバイダーの実際の利用制限と料金表示の取得方法。

### D-03: プレビュー上の指摘を対象付きの修正へつなぐ

- 対象状態: 生成後の修正。
- 変更前または現状: 修正は右ペインの自由入力で行い、どの画面・要素への指示かを文章で再説明する必要がある。仕様の版履歴はない。
- 提案: プレビューで画面または要素を選び、「ここを修正」から指示を入力する。対象ID、現在の仕様版、利用者の指示だけを改訂依頼へ渡す。戻ってきた案は、変更箇所と前版との差分を示して適用・破棄できる。各適用版を戻せるようにする。
- 根拠: 直接修正と前版復元は、AIの部分的な誤りからの回復を短くする。[Microsoft HAXの詳細編集パターン](https://www.microsoft.com/en-us/haxtoolkit/pattern/g9-b-rich-and-detailed-edits/)
- トレードオフ: 要素IDの安定性と版の保存が必要。
- 受入条件: 1画面の文言を変えても、他画面の未変更部分を保持する。適用前に差分を確認でき、前版へ戻せる。
- 未検証事項: 選択対象の粒度と差分表示の読みやすさ。

### D-04: 複数工程の進捗と中止を明示する

- 対象状態: 仕様案生成、Markoビルド、検査、保存。
- 変更前または現状: 処理中表示と失敗ログ、ログアウト時の中断はあるが、利用者が通常の処理を中止する入口はない。
- 提案: 案件行に現在工程、経過時間、中止を置く。完了した工程と失敗工程を分け、成功済み成果物を維持する。進捗率を推測で表示しない。
- 根拠: 待ち時間中も別案件を操作できるため、元案件へ戻るときに進行位置と次の行動が必要。
- トレードオフ: 工程ごとの中断と一時ファイルの扱いを統一する必要がある。
- 受入条件: ビルド中に中止しても未検証HTMLを完成品として表示せず、元の仕様から再実行できる。
- 未検証事項: 実際の処理時間分布と中止頻度。

## 6. 権限・承認・共有制御

- 計画を見せる条件: 将来、複数ファイルの変更や外部公開をエージェントが行う場合。現行の仕様提案とローカルHTML生成には常時の計画確認を追加しない。
- 直前承認が必要な操作: 将来の共有・公開・削除。モデルへの送信は送信対象を示したうえで利用者の明示操作とする。
- 許可の範囲と期限: 接続はプロバイダー単位。送信文脈は案件単位で設定し、送信前に変えられる。
- 拒否後の挙動: 外部送信を選ばなくても仕様の閲覧・ローカル編集は続けられる。拒否した内容を別経路から送らない。
- 一時停止・再開・中止: ログアウト時の停止は実装済み。通常ジョブの中止はD-04で追加し、再開は明示的な再試行とする。
- 取消・補償操作: 仕様の前版復元。送信済みデータは取り消せないと示す。
- モデル外の安全境界: 現行のPi呼び出しはツール等を無効化している。将来ツール実行を増やす場合はOS権限と実行環境で制限する。
- 監査記録: 仕様版、モデル、送信文脈の種類、工程結果、成果物への参照を記録する。会話本文や資格情報を無条件に記録しない。

## 7. 信頼・倫理・アクセシビリティ

- 根拠と適用範囲: 「構造チェック合格」と「仮説に必要な操作を確認済み」を別状態にする。どの仕様版・操作に対応するか明示する。
- 不確実性の伝え方: 未対応の動作と仮データは該当操作の近くに表示する。AIの流暢な説明を動作の証拠としない。
- データ利用と記憶: 案件のローカル保存とモデルへ送る文脈を区別する。資格情報は案件に含めない。
- 異議申立てと救済: 誤った仕様は部分修正、破棄、前版復元で扱う。共有後の訂正経路は共有機能を設計する時点で定義する。
- 影響を受ける人: 仕様に含まれる対象利用者、実データの本人、成果物を見る協力者。
- キーボードと支援技術: 操作範囲の表示、文脈選択、差分、適用、版復元、中止にキーボードで到達できることを受入条件にする。VoiceOverによる通し操作は未検証。
- 代替操作: プレビュー要素の選択は画面一覧からも行えるようにし、色だけで動作範囲を示さない。

## 8. 検証シナリオ

| 種別 | 手順 | 期待結果 | 証拠 | 状態 |
|---|---|---|---|---|
| 正常系 | 主要操作を指定し、仕様を生成してプレビューする | 実際に動く範囲が仕様とHTMLで一致する | 代表案件の操作記録 | not run |
| 誤解系 | 本文切替を要求するがビルダーが未対応 | 未対応と生成前に分かり、静的比較か実装追加を選べる | 仕様・UI・HTMLの比較 | not run |
| 誤出力系 | AIが無関係な画面まで修正する | 差分で検出し、適用せず前版を保持できる | 版差分と案件状態 | not run |
| 副作用系 | 過去の会話を除外して送信する | 除外部分が外部入力へ入らない | UI選択と実際のPi入力の照合 | not run |
| 復旧系 | ビルド中に中止し、再試行する | 入力と前回成功プレビューが残り、途中HTMLを表示しない | 状態と出力ファイルの確認 | not run |

## 9. 受入条件

| ID | 条件 | 検証方法 | 責任者 | 停止条件 |
|---|---|---|---|---|
| AC-01 | 主要操作ごとに動作範囲が表示され、HTMLと一致する | 代表案件で仕様と実操作を対照 | 実装・デザイン担当 | 未対応操作を動作済みと表示したら公開停止 |
| AC-02 | 除外した文脈がモデルに送られない | 送信入力を実際に照合 | 実装担当 | 除外内容の送信が起きたら機能停止 |
| AC-03 | 改訂は局所的で、前版へ戻せる | 複数画面を持つ案件で差分と復元を確認 | 実装担当 | 無関係な画面が消え、戻せない場合は未達 |
| AC-04 | 処理の中止で途中成果物を完成品扱いしない | 各工程で中止・再試行 | 実装担当 | 未検証HTMLが成果物に残れば未達 |

## 10. 未検証事項と次の一歩

- 未検証: 実利用者の理解、プレビュー上の部分修正の操作性、VoiceOver、各プロバイダーの利用量表示、生成中止の実機挙動。
- 残存リスク: 動作範囲を表示するだけでは主要仮説を試せない案件が残る。必要な動作を追加する優先順位は代表案件で判断する。
- 次に行う最小検証: 日記の「内容を固定し語り口だけ変える」案件を使い、仕様に書かれた操作と実際のHTMLの状態変化を表にする。その差分をv0.0.4の最初の実装範囲とする。

## 11. v0.0.4実装検討（現行コードとの照合）

### 実装状況

| 案 | 現状 | v0.0.4で必要な差分 |
|---|---|---|
| D-01 操作とプレビューの一致 | 一部のみ。画面遷移と入力値の表示更新は動くが、操作単位の分類はない | 最優先で実装する |
| D-02 送信文脈の確認・除外 | 未実装。会話履歴と現在仕様を自動でプロンプトに含める | D-01の後に送信境界を設計する |
| D-03 対象付き修正・差分・復元 | 一部のみ。改訂案の適用・破棄はあるが、対象IDと版履歴はない | 安定した要素IDをD-01で先に用意する |
| D-04 工程表示・通常の中止 | 一部のみ。内部の中断機構と粗い進行表示はあるが、通常の中止入口はない | 後続の小さな機能として実装できる |

この判定は`builder/wireframe-runtime.js`、`builder/build-wireframe.mjs`、`WireframeReviewSpec.swift`、`PiChatService.swift`、`WorkspaceModel.swift`、`BuildService.swift`を照合したもの。アプリや生成HTMLの実機操作による確認はまだ行っていない。

### D-01の実装境界

新規仕様では`screen.operations[]`を任意の構造化宣言として追加し、参照される`action`と`panel`にも安定した`id`を付ける。たとえば日記の本文切替は次のように表す。旧仕様の`action`や`panel`にIDがなくても読み込めるよう、旧形式は読み取り時に画面IDと要素位置から表示用IDを派生する。生成後の修正対象には、派生IDを恒久IDとして使わない。

```json
{"id":"tone-changes-body","label":"語り口で本文が変わる","triggerRef":"tone","expectedEffect":{"kind":"replace-panel-text","targetRef":"diary-body"}}
```

この宣言は利用者の期待を表すだけで、実装済みの証明には使わない。`replace-panel-text`がランタイムに存在しない間は「未対応」とする。

1. **検証する操作を構造化する。** 新規仕様には、主要な操作ごとに安定ID、表示名、起点の画面・要素、期待する状態変化を持たせる。ビルダーは既存のボタン・入力欄も必ず自動列挙し、宣言された期待と結び付ける。画面の`testNote`など自由文だけから完全な操作一覧を推定したと扱わない。旧仕様では自動列挙した操作を保守的に分類し、自由文中の動作は「照合待ち」と示す。
2. **判定をビルダー側で一度だけ行う。** AIが「動作する」と自己申告する欄は設けない。`builder/`の独立した能力判定モジュールを単独実行して、仕様上の期待とランタイムが実装する状態変化を照合する。操作ID、判定、根拠、仕様版を含むレポートを生成前のSwiftUI画面と生成HTMLの両方へ渡す。仕様編集中の非同期判定は仕様版で照合し、古い結果を現在の仕様として表示しない。
3. **4つの表示を厳密に使う。** 「動作する」は期待した値反映まで実装した操作、「画面遷移のみ」はボタンによる遷移だけ、「表示のみ」は静的な内容、「未対応」は期待した変化をランタイムが実装しない操作とする。たとえば`select`の値を`value`へ映すことと、選択で`panel`本文を書き換えることは別の操作として扱う。後者は現行ランタイムでは未対応と判定する。ボタンのラベルが「保存」でも、遷移だけなら保存済みとは表示しない。
4. **検査と保存をつなぐ。** Marko生成時に同じレポートをHTMLへ含め、構造検証時に操作IDと表示の対応を検査する。レポートと生成元仕様の版を成果物に記録する。未対応の操作があっても生成は許すが、「この仮説の操作確認はまだできない」と生成前・プレビューの両方に表示する。構造検証合格と操作確認済みは別状態にする。

最初の受入例は日記の3画面とする。「語り口の選択値表示」は動作すると示し、「語り口による本文差し替え」は未対応、「この語り口で保存する」は画面遷移のみと示す。画面上の表示、HTML内の表示、実際の状態変化が一致したときだけAC-01を満たす。本文差し替え自体の実装は、利用者がその動作を優先して検証したいと決めた後の別タスクとする。

### 実装順と変更候補

1. `builder/`に操作能力の判定モジュールと旧仕様の読み取り規則を追加する。
2. `PiChatService.swift`の仕様生成指示と`WireframeReviewSpec.swift`に操作宣言を追加する。宣言の欠落・不明な起点・未対応の期待を黙って成功扱いしない。
3. SwiftUIの仕様レビューに操作一覧と判定根拠を表示し、生成前に確認できるようにする。
4. `builder/wireframe.marko`と構造検証器に同じ判定結果を渡し、プレビュー内に操作ごとの表示を置く。
5. 代表案件で4分類と旧仕様を照合し、判定・HTML・実操作にずれがあればv0.0.4の完成としない。

D-02はPiへのプロンプト組み立て前に送信対象を確定する必要がある。D-03は要素IDと版履歴が先に要る。D-04は`JobCancellation`の既存経路を通常の中止ボタンへ接続できるが、ビルド途中の正本削除と再試行状態を工程ごとに確認してから公開する。

## 12. v0.0.4の実装結果

D-01の操作範囲表示を実装した。新しい仕様では`screen.operations[]`に期待する操作を宣言し、`builder/analyze-operations.mjs`がランタイムの実装範囲と照合して4分類を返す。宣言のない旧仕様ではボタン、入力と値表示の組を自動列挙する。AIの説明やボタン名だけで保存・本文切替を実装済みとは判定しない。

SwiftUIの仕様確認には期待する結果、操作の分類と理由を表示し、生成HTMLのサイドバーにも同じレポートを表示する。レポートには生成元JSONのSHA-256識別子を含め、成果物のプレビューは生成元の仕様を参照する。HTMLの構造検証では埋め込んだレポートと操作ID・分類・期待する結果・日本語ラベルの一致を検査する。未対応の操作があってもHTMLは生成でき、操作確認待ちと表示する。

v0.0.4で追加したのは検証可能な範囲の表示であり、`content-switch`による本文変更や実際の保存処理は実装していない。D-02〜D-04は継続課題である。実利用者による理解の確認とVoiceOverでの通し操作は未実施。
