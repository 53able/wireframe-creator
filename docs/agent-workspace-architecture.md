# エージェントと仕事を仕上げるMacワークスペース

> **構想メモ / 2026-09-23**
> OpenAI・AnthropicのサブスクリプションとPiを使い、入力から検証済み成果物までを一貫して扱うMacアプリの論点整理。

## 要約

**Piをエージェント実行基盤の第一候補として検証し、SwiftUIアプリが仕事の状態・権限・履歴・成果物を管理する構成を推奨する。AIとの往復を減らす際も、完成の判定条件は維持する。**

PiはOpenAI CodexとAnthropicを含む複数プロバイダー、サブスクリプション認証、エージェントループ、Skills、RPC／SDKの接続手段を備える。複数のAI実行環境をアプリ側でゼロから統合する負担を減らせる。一方、Piは標準状態でファイルやシェルの権限境界を提供しない。Macアプリ側に、アクセス範囲・承認・実行履歴の仕組みが必要となる。

最初の検証対象には、既存のwireframe-creatorスキルを使う。入力資料の指定から、ワイヤーフレーム生成、アプリ内プレビューと検証、成果物の保存までを一つのビルド工程として扱う。

効率化の目標は、同程度の依頼で**人とAIの往復回数、完了までの時間、手戻りを減らすこと**。品質は構造検証、ブラウザー操作、成果物レビューで確かめる。測定前に「何％速くなる」とは見積もらない。

## 目指す体験

利用者が依頼と資料を渡すと、アプリが作業計画を示し、エージェントの進行・確認依頼・成果物を一つの場所で扱う。利用者は途中で方向を直し、根拠や検証結果を見て、完成した成果物を保存できる。

**価値の中心はスキルの一覧ではなく、仕事の状態と成果物を最後まで追えること。**

## 推奨構成

```text
┌────────────────────── Macアプリ ──────────────────────┐
│ SwiftUI: プロジェクト / 実行状況 / 承認 / 成果物 / 履歴 │
│ Workflow Core: 状態遷移 / 権限方針 / 保存 / 再開        │
└─────────────────────────┬──────────────────────────────┘
                          │ 型付きコマンド・イベント
                 ┌────────▼────────┐
                 │ Pi Runtime       │
                 │ Node側ローカル実行 │
                 └────┬────────┬────┘
                      │        │
               Skills / 拡張  モデル認証・生成
                               ├─ OpenAI Codex OAuth
                               └─ Anthropic OAuth
                      │
                      ▼
           選択されたプロジェクトフォルダー
```

### Macアプリ

- SwiftUIで、プロジェクト、実行タイムライン、承認待ち、成果物の三ペインを中心に構成する。
- PiのTUIをそのままアプリの画面にせず、アプリ固有のワークスペース体験を作る。
- PiとはRPCまたはSDKを通じて接続し、UIと実行ランタイムを分離する。

### Workflow Core

- 実行状態を `draft → queued → running → awaitingApproval → completed / failed / cancelled` のように管理する。
- Piからの出力、利用者の指示、承認、成果物、検証結果を時系列イベントとして記録する。
- Piの会話セッションと、アプリの「仕事」レコードを分ける。Piセッションは会話の枝・モデル実行を担い、アプリはタスク全体・進捗・納品物を担う。
- アプリを閉じても状態を復元できるよう、状態とイベントをローカルに永続化する。MVPではアプリを実行履歴と状態データの唯一の書き込み元にする。
- 入力資料から抽出した事実、仮定、未解決事項、検証目的を短いブリーフとして保存し、後続工程へ引き渡す。追加のAI呼び出しには関係するブリーフ、変更箇所、検証失敗だけを渡す。

### Skillsと成果物

- `SKILL.md`、`scripts/`、`references/`、`assets/`を含む現在のスキル形式を維持し、アプリは既存スキルを読み込む。
- Skillは「専門手順」、Piは「その手順を実行するエージェント」、Macアプリは「仕事を管理する環境」と責務を分ける。
- 入力と完成物は利用者が選んだプロジェクトフォルダーに置く。実行ログや検索用メタデータはアプリのローカルデータとして保持し、成果物の所在は常に明示する。

## AIとの往復を減らし、品質を保つ設計

wireframe-creatorには、要件から検証目的と画面を決める判断工程と、進捗更新、テンプレート生成、構造検証、プレビュー、最終化の定型工程がある。MVPでは後者をアプリと既存スクリプトが実行する。AIには対象ユーザー、主要フロー、必要な状態、修正方針の判断を担わせる。

| 工程 | 往復を減らす方法 | 次へ進む条件 |
| --- | --- | --- |
| 入力整理 | 資料を一度読み、事実・仮定・不明点をブリーフに固定する | 対象ユーザー、検証目的、主要タスクが定義できる |
| 確認 | 成果物を大きく変える不明点をまとめて質問する | 回答または明示した仮定をブリーフへ反映する |
| 設計・生成 | ブリーフと既存テンプレートから一つの主要フローを作る | 必要な画面、状態、遷移、前提、未解決事項を含む |
| 構造検証 | 既存の検証スクリプトを自動実行し、エラー箇所だけを修正する | HTML構造、画面ID、遷移先、自己完結性が合格する |
| ブラウザー検証 | 実画面で主要フロー、狭幅・広幅、キーボード操作を確認する | 実施項目が合格し、未実施項目には理由が付く |
| 最終化 | 既存の最終化手順をアプリが進める | 正本HTMLの再検証、表示確認、プレビューサーバーの管理が完了する |

人への確認は、入力から判断できず結果が大きく変わる事項と、成果物のレビューに集中させる。質問をまとめても、新たな矛盾や重要な不足が見つかれば追加で確認する。判断結果はブリーフに記録し、次の工程で同じ質問を繰り返さない。

AIによる修正は、失敗した検証項目と関連するファイル範囲を渡して行う。修正後は同じ検証を再実行する。AI修正の試行回数には上限を設け、解決しない場合は失敗理由と残る成果物を示して停止する。**検証に失敗した実行を完成扱いにしない。** 最終化の節目では、途中の部分検証に加えて主要フロー全体を確認する。

品質にはHTMLの正しさだけでなく、検証目的に対して画面が適切かという判断も含める。ブリーフと成果物を並べてレビューし、利用者による評価を実施していない成果物を「ユーザー検証済み」と表現しない。絶対的な品質保証はできないため、MVPでは現行スキルと同じ合格条件を満たし、レビューで見つかる問題を増やさないことを採用条件とする。

### 効果の測り方

現行スキルとMVPに同程度の依頼を与え、同じ成果物の合格条件で比較する。比較用の依頼には、新規作成、情報不足、改稿を含める。

- **効率:** 完了までの時間、AI呼び出し回数と使用量、人への質問回数、手動操作回数、修正回数。
- **品質:** 構造検証の合格率、主要フローの操作成功率、狭幅・広幅・キーボード確認の実施率、最終レビューで見つかった問題の数と重大度。
- **採用判断:** 品質指標が現行より悪化せず、効率指標に改善が見られること。満たさなければ短縮した工程を特定し、品質条件を戻して再評価する。

## HTMLビルド環境

MacアプリはHTMLの生成から保存までを管理する。利用者はアプリ内で編集中の画面を確認し、完成時には外部依存のない単一HTMLを受け取る。**この節で述べる新規生成の構成（Marko 6＋Tailwind CSS 4）は、Macアプリ（`Sources/AgentWorkspace`）に限った経路である。** エージェントスキル本体（`SKILL.md`が定義する経路）はPico CSS v2.1.1を正式仕様として継続しており、本書はスキル本体の生成経路を変更するものではない。意味的HTML、操作可能な画面遷移、検証結果の記録は成果物契約として維持する。Pico CSS版の既存成果物（スキル本体が生成するもの、および旧経路のMacアプリ成果物）は引き続き読めるようにし、Macアプリの新しい正本にはPico CSSを含めない。

なお、スキル本体（`VERSION`ファイル、現在3.1.0）とMacアプリ（`packaging/Info.plist`等、現在0.0.4）は別々にバージョン管理されている。

```text
入力資料 → 検証ブリーフ → 画面・遷移JSON
                         ↓
          Markoで意味的HTMLを生成
          Tailwindで必要なCSSを生成
                         ↓
          CSS・画面ランタイムを内包
                         ↓
            構造検証 → アプリ内プレビュー
                         ↓
              操作検証 → 正本HTML保存
```

### 採用構成と現在の実装

- `builder/wireframe.marko`が画面の意味的HTMLと共通レイアウトを定義する。AIの通常の編集対象は`examples/wireframe.json`と同じ形のデータであり、画面を追加してもテンプレートのHTMLを複製しない。Markoはサーバー側でHTML文字列を返せる。[MarkoのテンプレートAPI](https://markojs.com/docs/reference/template)
- `builder/wireframe.css`をTailwind CSS 4のCLIでコンパイルし、使用するクラスのCSSとMITライセンス全文をHTML内へ埋め込む。画面構造と見た目の共通部分をビルダーへ寄せ、パレットは`slate`、`indigo`、`teal`から選ぶ。Tailwindはソース中のクラスを検出して必要なCSSを生成するため、動的にクラス名を組み立てず、テンプレート内に完全なクラス名を置く。[Tailwindのソース検出](https://tailwindcss.com/docs/detecting-classes-in-source-files)
- `builder/build-wireframe.mjs`が入力JSONの画面ID、ブロック種別、遷移先と入力値の参照先を検査し、Marko出力へCSSと画面切替スクリプトを内包する。`select`または`field`の値は同じ`key`を持つ`value`ブロックへ表示される。生成物にCDNや実行時のMarko依存は含めない。Python検証器はTailwindの新規成果物とPico CSSの旧成果物を区別する。
- 現在の実装では、SwiftUIアプリがPiとのチャット、人が読める画面構成のレビュー、Markoビルド、Python構造検証、完了時刻付きHTMLの保存、`WKWebView`での表示をつなぐ。案件ごとに会話、入力途中の文章、仕様、処理状態、成果物への参照を分け、Application Supportに自動保存する。旧スキルのPico CSS経路は維持する。既存HTMLのJSON移行、実行中プロセスの再起動後継続、旧進捗表示との統合は未実装である。

### MVP第1スライスの実装境界

`Package.swift`と`Sources/AgentWorkspace/`にmacOS用のSwiftUIアプリを置く。一つのウィンドウに案件一覧を常設し、選択中の案件についてPiとの会話、中央のプレビュー、右の「仕様／成果物」インスペクタを表示する。案件ごとに会話、入力、仕様、生成状態、成果物を分け、別案件の処理中でも切り替えて作業できる。仕様では内部JSONから対象ユーザー、検証目的、判断事項、画面と遷移、仮定を読み取り、日本語で表示する。修正指示から改訂案を一操作で作り、JSONの直接編集は詳細表示に置く。中央で構造チェックに合格したHTMLを表示する。仕様変更後も前回のプレビューを参照できるが、旧版であることを表示する。成果物では保存先とビルド・検証ログを確認できる。`scripts/run-mac-workspace.sh`は開発用の未署名`.app`を`dist/`に作成して起動する。

配布用には`scripts/package-mac-workspace.sh`で、Pi SDK／CLI、Node.js、Marko・Tailwind CSSの依存関係、画面テンプレート、構造検証スクリプトを`.app`内に収めたDMGを作成する。リポジトリ外で起動したアプリは同梱資材を参照し、HTMLを初期設定で「書類/Agent Workspace」へ保存する。Python 3は配布先の既存インストールを使う。Viteのキャッシュは読み取り専用アプリ内ではなく一時領域へ置き、依存関係の事前最適化を停止する。現在のDMGはアドホック署名で、Appleの公証は未実施である。

アプリの「モデルプロバイダー」からOpenAI Codex／AnthropicのOAuth認証を開始し、Pi SDKの通知を使ってブラウザーへ案内する。確認コードが必要な場合は同じウィンドウで入力する。認証状態と提供モデルはPi SDKから取得し、案件ごとのモデルは一覧から選ぶ。認証情報はPiの資格情報保存領域に置き、案件データには含めない。会話では同梱Pi CLIを各ターン非対話モードで起動し、案件ごとの会話履歴をプロンプトへ渡す。通常の会話と仕様案生成では`--no-tools`、`--no-extensions`、`--no-skills`、`--no-context-files`を指定する。利用者が`/スキル名`を明示した会話では`~/.agents/skills`から選択した1件だけを`--skill`で読み込み、Piの標準ファイル・シェルツールを許可する。スキルの作業ディレクトリは案件の保存先とする。選択したスキルのディレクトリ内にある参照ファイルの読み取りを除き、ツール呼び出しはアプリ側の承認ゲートで一件ずつ許可・拒否し、操作概要を案件の会話へ残す。OSサンドボックスは未実装であり、許可した操作は利用者権限で動く。Piの標準ツール以外を前提にするスキルは、読み込み自体は可能でも、その専用機能を実行できない。利用者の依頼は標準入力から渡す。ストリーミング応答とPiセッションの再開は次の実装対象とする。[Pi CLI](https://pi.dev/docs/latest/cli)、[Piの認証](https://pi.dev/docs/latest/providers)、[Piのモデル選択](https://pi.dev/docs/latest/models)

チャットの画像添付はFinderからのドラッグ＆ドロップとファイル選択に対応する。画像は案件ごとにApplication Supportへコピーし、会話と送信前の添付情報を案件スナップショットに保存する。HEICなどPi CLIが直接読めない形式はPNGへ変換する。画像対応モデルに限り、テキストは標準入力、画像はPi CLIの`@絶対パス`引数として渡す。直近の会話画像を仕様案生成と再試行にも引き継ぐ。画像は1枚20MB以下、送信前は8枚までとする。

v0.0.3ではプロバイダー単位のログアウトを追加した。ログアウト操作時にアプリの利用許可を即時に外し、そのプロバイダーで進行中のPi（会話・仕様案生成）ジョブを中断する。Piの子プロセスに終了を要求し、遅着結果はジョブIDで棄却する。ログアウト状態はアプリに保存し、SDK側の認証削除が失敗した場合や環境変数に資格情報が残る場合も、アプリ内で再ログインするまでそのプロバイダーの手順を再開しない。ローカルのHTML生成（Marko/Tailwindビルドと構造検証）はモデル接続を必要としないため、進行中のジョブはログアウトの影響を受けず継続する。案件の閲覧と編集は可能だが、送信、改訂案の適用、生成、再試行は利用可能モデルがある場合に限る（UI側の可用性判定によるもので、生成処理自体がプロバイダーに紐づくわけではない）。ほかの接続済みプロバイダーの案件は継続できる。

アプリは入力JSONを一時ファイルへ書き、Markoビルダーで単一HTMLを生成してからPython検証器を実行する。合格した本文だけを新しいタイムスタンプ付きファイルにコピーし、正本を再検証してからプレビューへ渡す。検証失敗時は正本を残さない。`WKWebView`はプレビューするHTMLファイル自身だけを読み取り範囲に指定し、独立した非永続データストアを使う。[Apple: ローカルファイルの読み込み](https://developer.apple.com/documentation/webkit/wkwebview/loadfileurl%28_%3Aallowingreadaccessto%3A%29)

案件ごとの会話履歴とJSONの編集はアプリ終了後も復元する。Piの仕様案が生成中に人の編集と競合した場合は自動上書きせず保留し、インスペクタで確認・適用・破棄できる。次のスライスでは版差分と検証目的の比較を充実させる。

ローカルでの生成例は次のとおり。出力先に既存ファイルがあるとビルダーは上書きを拒否する。

```bash
npm ci
node builder/build-wireframe.mjs examples/wireframe.json dist/wireframe.html
python3 scripts/validate-wireframe.py dist/wireframe.html --min-screens 2 --require-actions
```

### 移行順序

**第1段階では既存のPythonプレビュー・検証・最終化スクリプトをアプリから実行する。** HTML本文の新規生成はMarkoビルダーへ切り替える。アプリがプレビュー用ファイル、localhostサーバー、検証コマンド、正本の最終化を管理する。プレビューは同じURLをアプリ内の`WKWebView`で開き、エージェントがURLやPIDの受け渡しを毎回判断する工程を減らす。サーバーの所有、停止、残存状態は引き続きアプリが記録する。Appleは`WKWebView`にHTMLやローカルファイルの読み込みとJavaScript実行のAPIを提供している。サンドボックス化する場合は、localhostへの接続と待ち受けに必要なネットワーク権限も検証する。[WKWebView](https://developer.apple.com/documentation/webkit/wkwebview/)、[ネットワーク権限](https://developer.apple.com/documentation/xcode/configuring-the-macos-app-sandbox)

**第2段階ではAIの変更対象を画面・遷移JSONに限定する。** 画面ID、表示文、操作先、前提、未解決事項を構造化し、固定のMarkoテンプレートと画面ランタイムからHTMLを組み立てる。改稿時は対象画面のデータだけをAIに渡し、ビルダーが単一HTMLを再生成する。共通レイアウトや部品を変更するときだけMarkoとTailwindのソースを編集する。自由なHTML編集が必要な案件の扱いは、既存スキルとの成果物比較を経て決める。

**第3段階でlocalhostサーバーを外せるか検証する。** ビルド完了イベントから`WKWebView`へ更新を通知し、作業中HTMLをローカルファイルとして読み込む方式を比較する。画面位置、入力値、フォーカスを保つ現在のホットリロード契約と同等にできた場合に切り替える。Appleは`WKWebView`でローカルファイルを読み込む際に読み取り範囲を指定するAPIを提供している。[WKWebViewの読み込みAPI](https://developer.apple.com/documentation/webkit/wkwebview/)

### ビルドの品質条件

- 生成時はMarko、Tailwind CSS、テンプレート、画面JSONの版を記録し、同じ入力から同じHTML本文を再現できるようにする。完了時刻付きの正本ファイル名は最終化時に一度だけ決める。
- 構造検証に失敗したHTMLを正本として保存しない。プレースホルダー、遷移先、外部参照、内包CSSの版とライセンス表記を検査する。旧Pico CSS成果物は既存の固定版検査を使う。
- プレビュー表示の成功と、画面操作の成功を別々に記録する。主要フロー、狭幅・広幅、キーボード操作を確認する。
- `WKWebView`での確認に加え、配布する単一HTMLをファイルとして開いて再検証する。対象ブラウザーでの動作保証を求める場合は、そのブラウザーでの検証結果も残す。
- プレビューには独立したWebデータストアを使い、生成HTMLからの外部移動とアプリへのメッセージ受信を許可範囲内に制限する。[WKWebsiteDataStore](https://developer.apple.com/documentation/webkit/wkwebsitedatastore)
- 正本は既存ファイルを上書きせず保存し、一時プレビューや進捗表示を含めない。ビルド失敗時は前回の正本と作業データを保持する。

### ビルド効率の測定

AI呼び出し数に加え、入力確定から初回プレビューまでの時間、変更からプレビュー更新までの時間、ビルド・検証・最終化に要した時間、ビルド起因の再試行回数を記録する。第2・第3段階への移行は、これらの改善と品質条件の維持を確認して決める。

### OctaneJSの採用判断

OctaneJSはコンパイル時にDOM更新を最適化するUIフレームワークで、反復表示の多い画面に適する。公式ベンチマークには`chat-stream`や大量のDOM操作が含まれる。ただし、その数値はワイヤーフレーム生成やmacOSの`WKWebView`で測ったものではない。公式ドキュメントは現在ベータ版と記し、Node.js 22.22.2以上、コンパイラーとVite等のビルド連携を求める。[OctaneJS概要](https://octanejs.dev/)、[導入手順](https://octanejs.dev/docs)、[ベンチマーク](https://octanejs.dev/benchmarks)

現在のwireframe-creatorは、少数の画面を切り替える短いJavaScriptと、単一HTMLを成果物とする。Macアプリ本体はSwiftUI、プレビューは`WKWebView`という構成なので、OctaneJSを導入してもAI応答時間、PythonによるHTML生成、最終検証の時間には直接効かない。初期MVPでは依存関係に加えず、**アプリ内の画面編集や進捗表示でDOM更新が実際に律速になった場合の候補**とする。

評価する際は、同じ画面・操作を現在の軽量ランタイムとOctaneJSで作り、対象Macの`WKWebView`で初回表示時間、更新遅延、メモリ使用量、生成HTMLのサイズ、ビルド時間を比較する。単一HTMLへのCSS・JavaScript内包、画面遷移とキーボード操作の合格も必須とする。描画の改善がビルド負担と成果物サイズの増加を上回る場合に採用する。

## Piを使う理由と確認事項

### 強み

- Piはエージェントループと複数プロバイダー接続を提供するため、各社CLIの個別統合より共通の実行モデルを作りやすい。
- 現行ドキュメントはOpenAI CodexのChatGPTサブスクリプションOAuthとAnthropic Claude Pro／Max認証を案内しており、想定する契約形態と合う。
- Skills、拡張、RPC、SDKを持ち、既存のファイルベースのスキル資産を活かせる。
- MITライセンスで公開されている。

### 主なリスク

- PiのREADMEは、標準でファイル・プロセス・ネットワーク・認証情報への権限管理を備えず、起動元ユーザーの権限で実行することを明記している。**ワークスペースの安全境界はアプリ側で設計する必要がある。**
- Piの拡張やスキルは実行可能コードやエージェント指示を含み得る。インストール元、変更差分、実行権限を利用者に見せる必要がある。
- サブスクリプション認証の技術対応と、各プロバイダーの利用条件上の許可は別問題。認証方式・モデル・制限は変わる可能性があるため、製品化の前に公式条件とPiの現行実装を再確認する。
- macOS App Sandboxでは、子プロセスも親アプリのサンドボックスを継承する。任意のローカルCLIを広い範囲で実行する設計は、配布方式・権限モデルと早期に整合させる。

### 安全設計の最低ライン

1. アプリには利用者が選んだフォルダーだけを許可し、アクセス権はsecurity-scoped bookmarkで再起動後も管理する。
2. ファイル書き込み、シェルコマンド、ネットワーク操作などを、用途と対象が分かる承認単位に分ける。
3. Pi標準のファイル操作・シェル実行をそのまま許可しない。アプリ側の仲介ツールへ置き換えるか、Piプロセス自体を制限された環境で起動する。操作の主体・対象・結果をログに残す。
4. 認証情報をアプリの実行ログやプロジェクトフォルダーに保存しない。公式の認証経路とOSの安全な資格情報保存を使う。
5. MVPでは実行をフォアグラウンド中心とし、アプリ終了後も処理を続ける仕組みは後から判断する。

## 配布方式の判断

任意のCLIを起動し、利用者が選んだリポジトリを広く操作する機能が中核なら、Mac App Store向けApp Sandboxとの適合性が課題になる。Appleによると、サンドボックス化されたアプリが起動する子プロセスも親のサンドボックスを継承する。**プロジェクトフォルダー限定で動かすMVP**を前提に、App Store配布と直接配布の両方で必要な制約を早めに検証する。

## MVP検証

既存のwireframe-creatorスキルを一つの縦切りとして、以下を確認する。

1. Macアプリからプロジェクトフォルダーと入力資料を指定できる。
2. Pi経由でサブスクリプション認証済みのOpenAIまたはAnthropicモデルを選び、実行できる。
3. 実行中の進捗・質問・承認待ち・エラーをアプリ内で追える。
4. 生成HTMLと検証結果を同じ実行にひも付けて確認できる。
5. 実行をキャンセルし、失敗した場合は原因と再開可能な状態を確認できる。
6. アプリを再起動しても、実行履歴と完成成果物への参照が残る。
7. 許可していないフォルダーや操作へアクセスできないことを確認する。
8. 入力ブリーフを再利用し、AIへの同じ説明や人への同じ質問が繰り返されない。
9. 現行スキルと同じ検証条件で比較し、品質指標を悪化させずに往復回数または完了時間を減らせる。
10. アプリ内プレビューの更新から正本HTMLの再検証・保存まで、ビルド状態を一つの実行履歴で追える。

この縦切りで、PiのRPC／SDK接続、サブスクリプション認証、権限境界、イベント記録、成果物管理の実現性を判断する。複数エージェント協調やバックグラウンド常駐は、その後に追加する。
