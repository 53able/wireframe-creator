# AIインターフェース設計／レビュー: Agent Workspace MVP

この文書はモードレスUIへの変更前に評価した記録。仕様確認シートの改善内容と残る課題は[モードレスUI設計レビュー](agent-workspace-modeless-ui-review.md)を参照。

## 1. 結論

- 判定: 改善が必要。
- 主要判断: 会話から仕様案を作り、日本語の確認画面を経てプレビューへ進む流れは成立している。次の焦点は、**プレビューで実際に動くことと、仕様が約束することを一致させること**、および作業を失わずに修正できること。
- 最大リスク: 直近の日記の例では「語り口を変えると本文だけが変わる」と仕様に書かれる一方、生成HTMLは選択値の表示だけを変え、本文は固定のまま。利用者が確かめたい仮説を、動かないプレビューで判断してしまう。
- 優先度: P0＝挙動の一致と作業の保存、P1＝AIに渡す文脈・工程・エラーの可視化、P2＝開始画面と設定の整理。

## 5. 主要な設計判断

### D-01: 検証する操作を動かすか、模擬と明示する

- 対象状態: 仕様確認、プレビュー、保存。
- 変更前または現状: `select`は対応する`value`表示だけを更新し、`panel`本文は固定。「保存する」ボタンは画面遷移のみ。構造チェック合格後は「検証済みHTML」と表示する。
- 提案: 仕様の各操作へ「動作する／画面遷移のみ／表示だけ」を付ける。主要仮説に必要な動きがビルダーで表現できなければ、プレビュー作成前に警告し、動作を追加するか検証対象を狭める。日記例では語り口ごとの本文表示と選択後の状態を実装するか、静的な比較画面へ変更する。「検証済み」は「構造チェック合格」に改める。
- 根拠: 見た目が整ったプレビューほど挙動まで正しいと受け取られやすい。現行バリデータはHTMLの構造を確認するが、仮説との一致は確認しない。
- トレードオフ: 対応できない挙動を明示すると、即座に生成できる案件が減る。
- 受入条件: 日記例で語り口を変えると本文だけが変わり、材料と出来事は一定。実装しない場合は「本文は切り替わりません」を生成前とプレビュー内に表示し、その操作を検証済みと呼ばない。
- 未検証事項: 実際の利用者が必要とする動作の粒度。

### D-02: 作業単位を保存し、失敗から戻せるようにする

- 対象状態: 会話、仕様案、生成、再試行。
- 変更前または現状: 会話と仕様JSONは`WorkspaceModel`のメモリ上にあり、アプリ終了後の復元処理がない。失敗後は同じ仕様で再試行できるが、版比較や部分復元はない。
- 提案: 会話、選択した文脈、仕様案、生成物への参照を一つのプロジェクトとして自動保存する。仕様改訂ごとに版を残し、失敗時には「入力を修正」「同じ仕様で再試行」「前版を開く」を分ける。
- 根拠: 生成は確率的で、同じ再試行でも仕様案が変わりうる。制作体験では途中成果の消失が大きな損失。
- トレードオフ: ローカル保存の容量、削除・保持期間の設計が必要。
- 受入条件: 仕様確認中・ビルド失敗後のどちらで再起動しても、会話、仕様案、直前の成功プレビューへ戻れる。
- 未検証事項: 保存期間と削除の利用者希望。

### D-03: 送信範囲を見せ、文脈を利用者が制御する

- 対象状態: 会話送信、仕様案の生成。
- 変更前または現状: UIは「会話中にファイルやシェルを操作しない」と伝える。実際にはPiへ会話履歴全体と現在の仕様JSONを渡すが、送信範囲はUIに出ない。
- 提案: 初回送信前と仕様ファイル読込後に、接続先と送信対象を短く提示する。「過去の会話を含める」「現在の仕様案を含める」を確認・除外できるようにする。全文を毎回含める必要がない場合は、利用者に見える要約を使う。
- 根拠: ファイル操作の禁止と外部送信は異なる境界。日記や他者の情報が混じる例では特に重要。
- トレードオフ: 文脈を減らすと提案の一貫性が落ちる場合がある。
- 受入条件: 送信直前に対象を確認でき、除外した内容はPi呼び出しへ渡されない。拒否してもローカル編集を続けられる。
- 未検証事項: Piと各プロバイダーのデータ保持条件、認証方式、費用表示の取得方法。

### D-04: 仕様確認を「判断」の画面にする

- 対象状態: 仕様案のレビュー。
- 変更前または現状: 日本語の目的、画面、操作、仮定、未解決事項が読める。修正はシート下部の自由入力からチャットへ戻り、返答後に再度「仕様案を作る」必要がある。
- 提案: 最上部に「今回確かめること」「主要な操作」「動かない部分」を3項目で要約する。各画面カードに直接「この画面を直す」を置き、該当箇所を指定して改訂する。改訂前後の差分を人が読める文章で示す。JSONは詳細編集のままでよい。
- 根拠: 現在の二段階の改訂操作は手数が多く、長い仕様のどこが変わったか分かりにくい。
- トレードオフ: 差分表示と部分更新の実装が増える。
- 受入条件: 利用者がJSONを読まずに、主要仮説・遷移・模擬操作・改訂箇所を確認できる。
- 未検証事項: 画面カードの情報量と確認にかかる時間。

### D-05: 失敗表示を次の一手に結びつける

- 対象状態: Pi接続失敗、仕様不正、ビルド失敗。
- 変更前または現状: 右ペインのログに終了コードや技術的詳細が出る。再試行ボタンはあるが、同じ仕様が不正なら同じ失敗を繰り返す。
- 提案: エラーを「接続／仕様／生成／保存」に分類し、対象画面・項目、原因、修正候補、成功済み工程を表示する。技術ログは折りたたみ、仕様エラーは確認シートの該当箇所へ戻す。
- 根拠: これまでに`inputType`や`palette`の形式エラーが起きており、終了コードでは利用者が修正判断できない。
- トレードオフ: エラーの分類と日本語化を保守する必要がある。
- 受入条件: 同じ入力を再試行しても成功しないエラーでは、再試行を主ボタンにせず、修正箇所へ誘導する。
- 未検証事項: 利用者が修正に要する時間。

### D-06: 開始と設定を成果に沿って配置する

- 対象状態: 新規作業。
- 変更前または現状: 最初にチャット、空のプレビュー、モデルID文字列が見える。何を入力すれば良いかは最初のエージェント発話に依存する。
- 提案: 「何を確かめたいか」から始める短いカードを置き、対象ユーザー・仮説・主要操作の例を用意する。チャットはそのまま残す。モデル名は接続設定へ移し、通常画面には接続状態を示す。
- 根拠: このアプリの成果は会話そのものではなく、検証可能な試作品。モデルIDは多くの利用者にとって判断材料になりにくい。
- トレードオフ: 自由入力だけの画面より開始画面が増える。
- 受入条件: 初回利用者がモデルIDを編集せずに、対象と仮説を入力して仕様案まで進める。
- 未検証事項: 開始カードが経験者の速度に与える影響。

## 6. 権限・承認・共有制御

- 計画を見せる条件: 外部送信する内容が増える時、複数ファイルへ書く時、将来の共有機能を使う時。現行のローカルHTML一件の生成は、保存先と内容確認で十分。
- 直前承認が必要な操作: 将来の公開・他者への送信・削除。現MVPでのAI送信は利用者の「送信」「仕様案を作る」操作とし、その対象範囲を事前に見せる。
- 許可の範囲と期限: 接続先と送信文脈を作業単位で保持し、変更・取消できる。共有権限を包括的に許可しない。
- 拒否後の挙動: AI送信を拒否したらローカルの仕様編集・既存HTML確認を継続でき、別経路で送信しない。
- 一時停止・再開・中止: 現状は実行中表示のみ。提案はPi呼び出しとビルドの中止、保存した作業からの再開。中止後は途中ファイルを成果物として表示しない。
- 取消・補償操作: ローカル仕様の前版復元、生成ファイルのFinder表示と削除案内。外部送信の取消は不可と明示。
- モデル外の安全境界: 現行Pi呼び出しではツール、拡張、スキル、コンテキストファイルを無効化している。接続先・資格情報・通信先・保存先に関する独立した検証は未実施。
- 監査記録: 作業ID、仕様版、モデル・接続先、送信対象の種類、各工程の結果、成果物パスを記録する案。本文や個人情報を無条件にログへ残さない。

## 7. 信頼・倫理・アクセシビリティ

- 根拠と適用範囲: 「AIの提案」「構造チェック合格」「利用者による操作確認」を別の状態として表示する。どの仕様版から生成したプレビューかを示す。
- 不確実性の伝え方: 未解決事項は既に表示される。加えて、実装できない挙動や仮データを該当する画面・操作の近くへ表示する。AIの説明や流暢さを動作証拠にしない。
- データ利用と記憶: 現状はPiセッションなしで毎回履歴を再送し、アプリ内の会話と仕様案はメモリ保持。永続化、削除、送信先ごとの扱いを利用者へ明示する。
- 異議申立てと救済: 誤った仕様案やプレビューを修正・破棄・前版復元できることを先に整える。外部共有後の訂正経路は共有機能を追加する際に設計する。
- 影響を受ける人: 仕様に登場する利用者、日記の本人・子ども、生成物を見る協力者。仮の内容と本人の実データを区別する。
- キーボードと支援技術: チャット、仕様確認、プレビュー、エラー修正、保存までキーボードで到達し、状態更新を読み上げられることを受入条件にする。現時点でVoiceOverの通し操作は未実施。
- 代替操作: 色だけに依存せず状態を文字で表示する。生成HTMLの操作はボタン・選択欄があるが、フォーカス順や読み上げは未検証。

## 10. 未検証事項と次の一歩

- 未検証: 実ユーザーの理解・完遂率、VoiceOverとキーボードの通し操作、プロバイダー側のデータ保持と課金、アプリのネットワーク・資格情報境界。ここでの`pass`はコード上の導線確認だけを意味する。
- 残存リスク: 制作物の見た目と文章が整っていても、仮説に必要な挙動が欠ける。保存前のアプリ終了で作業が失われる。
- 次に行う最小検証: 日記例を一つの代表シナリオとして、仕様文・生成HTML・実際の操作を突き合わせる。P0の2点を直した後、初回利用者に「内容と語り口が分離しているか」をプレビューだけで説明してもらう。
