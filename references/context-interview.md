# コンテキスト逆質問プロトコル

ワイヤーフレームを描く前に、何を作るかではなく、何を学び、どの判断に使うかを揃える。入力資料に答えがある項目は再質問しない。回答がない項目は推論できるが、観測事実として扱わない。

## コンテキスト台帳

入力資料から次を埋める。各項目へ `observed`、`answered`、`inferred`、`unknown` のいずれかを付ける。

1. **問題と範囲**: 現在の問題、対象範囲、対象外
2. **対象ユーザー**: 役割、利用状況、現在の代替手段、主なペイン
3. **ユーザー成果**: 完了したいこと、得たい実用的・感情的メリット
4. **ビジネス成果**: 期待する行動変化と、わかる範囲の測定方法
5. **ソリューション境界**: 固定済みの案、変更可能な案、必須要素、禁止事項
6. **主要シナリオ**: 開始条件、主要タスク、完了・中断条件
7. **仮説**: 誰に何を提供すると、どの成果につながると考えているか
8. **最大リスクと学習**: 誤りなら案を見直す前提と、今回決めたいこと
9. **実験範囲**: ワイヤーフレームで見せる最小画面・状態と、観察する行動
10. **提供制約**: Web／モバイル／デスクトップ、画面幅、入力手段、アクセシビリティ、データ、技術、法務・運用上の制約

`inferred` には、推論根拠と確信度 `high`、`medium`、`low` を添える。ユーザー調査をしていない限り、ユーザーのニーズや行動を `observed` にしない。

## 逆質問の作り方

1. コンテキスト台帳を入力資料から先に埋める。
2. 欠落していても成果物をほぼ変えない項目は質問しない。
3. 欠落すると対象ユーザー、主要フロー、検証目的、またはスコープが大きく変わる項目だけを選ぶ。
4. 一度に質問するのは最大6問とし、番号付きの1メッセージへまとめる。
5. 冒頭に次を明記する。

> 分からない項目は「不明」で構いません。その場合は、提供資料と一般的な利用状況から推論し、仮定として明記して進めます。

6. 質問は、問題 → ユーザー → 成果 → ソリューション境界 → 最大リスク → 実験・制約の順にする。画面や機能の希望だけを先に聞かない。
7. 回答後、台帳を更新する。`不明`、無回答、判断保留の項目は、最も保守的で検証可能な案を推論し、正本HTMLの「前提」へ記載する。
8. 推論で複数案が同程度に成立する場合は、壁打ちモードとして推奨案と代替案を提示し、今回のワイヤーフレームで比較する判断軸を1つに絞る。
9. 矛盾する要求、保存先、既存正本の上書き可否、不可逆な外部操作は推論で決めない。

## 質問テンプレート

必要な項目だけを選び、固有の文脈に書き換える。

1. **問題**: 現在、誰のどの行動や業務で何が起きており、今回どこまでを対象にしますか？
2. **ユーザー**: 最初に扱う利用者の役割と利用状況、現在使っている代替手段は何ですか？
3. **成果**: 利用後に何ができる、またはどう感じられる状態を目指しますか？　成功時に変わる行動は何ですか？
4. **境界**: 必ず残す案・機能・制約と、ワイヤーフレームで変更してよい部分はどこですか？
5. **リスク**: 誤っていたらこの案を見直すべき、最も不確かな前提は何ですか？
6. **実験**: 今回のワイヤーフレームを見て何を決めますか？　必要な端末、主要シナリオ、エラー状態は何ですか？

## 推論して進める場合の既定

- 対象ユーザーは、入力資料で最も頻繁に具体的なタスクが記述されている役割とする。
- 主要シナリオは、そのユーザーが価値へ最短で到達する1フローとする。
- ビジネス成果は機能の完成ではなく、期待するユーザー行動の変化として置く。
- 最大リスクは、初期段階では実装容易性より「ユーザーがその価値を必要とし、使おうとするか」を優先する。ただし依頼が技術実現性の検証なら、その限りではない。
- 実験範囲は、最大リスクを露出する最小の画面・状態に絞る。
- 端末指定がなければWebを仮定し、320px前後と1280px前後で検証する。
- エラー状態は主要タスクの理解に影響する1件だけを選ぶ。

これらは事実ではなく、ワイヤーフレームで検証するための暫定仮定である。
