# プレビューサーバーのプロセス管理

プレビューサーバーを起動するときに読む。目的は、終了後のゾンビプロセスと意図しない稼働プロセスを残さず、静的HTML引継ぎに失敗して意図的に維持するサーバーだけを明示的に管理することである。

## 1. 起動時に所有権を記録する

1. 実行環境にプロセス管理ツールがある場合はそれを優先し、run ID、process handle、job IDなど停止と状態確認に使える識別子を保存する。
2. シェルで起動する場合は、起動した正確なPIDを直後に保存する。`pgrep`、ポート検索、プロセス名の部分一致から後で推測しない。
3. PIDだけでなく、対象HTMLの絶対パス、`PREVIEW_URL`、起動時刻を作業中の一時状態として保持する。
4. 同じ成果物用のサーバーが既にある場合は二重起動せず、所有者と生存状態を確認して再利用するか、前の所有者へ停止を依頼する。
5. `killall`、`pkill -f`、ポートを使用する全プロセスの一括停止は使わない。無関係なサーバーを巻き込む可能性がある。

## 2. 稼働中の状態を区別する

次の状態を混同しない。

- **managed-running**: 今回の作業が所有し、PIDまたはhandleを追跡している。
- **intentional-handoff**: 静的HTML引継ぎに失敗し、利用者の表示を切断しないため意図的に稼働を維持している。URLとPIDまたはhandleを報告する。
- **untracked-running**: 所有者または停止方法が不明な稼働プロセス。勝手に停止せず、残存リスクとして報告する。
- **stopped-and-reaped**: 終了を要求し、子プロセスなら `wait` または実行環境の同等APIで回収し、生存していないことを確認した。
- **zombie**: 終了済みだが親が回収していない状態。成功扱いにしない。

`intentional-handoff` はゾンビではないが、無期限に放置しない。次に再開する作業が同じURLとPIDまたはhandleを引き継ぎ、静的HTMLへの移行または明示的停止を行う。

## 3. 停止と回収

静的HTML引継ぎが成功した場合、または失敗・中断時にプレビューを維持する必要がない場合は、所有しているサーバーを次の順で終了する。

1. 保存したPIDまたはhandleが、起動時に記録したプレビューサーバーと一致することを確認する。
2. プロセス管理ツールの通常停止、または `SIGTERM` 相当の正常終了を要求する。
3. 上限付きで終了を待つ。無期限に待たない。
4. 期限内に終了しない場合だけ、プロセス管理ツールの強制停止または `SIGKILL` 相当を使う。
5. 今回のシェルまたはランナーが直接の親なら、`wait` または同等APIを必ず実行して終了状態を回収する。
6. PIDまたはhandleが生存していないこと、状態が zombie/defunct でないこと、`PREVIEW_URL` が応答しないことを確認する。
7. 停止確認後にPIDファイルや一時的なプロセス状態を削除する。

停止APIの成功応答だけで完了としない。生存確認とURL確認を別々に行う。

## 4. 中断・失敗時

- HTML生成、構造検証、ブラウザ接続が失敗して作業を終了する場合も、所有しているプロセスへ同じ停止・回収手順を適用する。
- 利用者がブラウザを操作中でも、静的HTML引継ぎが未完了ならサーバーを突然停止しない。`intentional-handoff` としてURLとPIDまたはhandleを報告する。
- セッション終了前に、追跡中の各プレビューサーバーを `stopped-and-reaped` または `intentional-handoff` のどちらかへ分類する。分類できない状態を残さない。
- 強制停止、状態確認、URL確認のいずれかを実施できなかった場合は `not run` と具体的な制約を報告し、「ゾンビを残していない」と断定しない。

## 5. 報告項目

完了報告へ次を含める。

- プレビューサーバー状態: `stopped-and-reaped | intentional-handoff | not run (reason)`
- 使用したPID、handle、またはjob ID
- 停止後の生存確認
- 停止後のURL応答確認
- `intentional-handoff` の場合は残存URLと、次回停止に使う識別子
